# Audit Pass 6 — 2026-06-16: UI flip root cause + full verification

## TL;DR

The audit pass 5 "UI flips back to CLOCKED OUT" fix only addressed the read-side
of `getActiveSegment`/`hasOpenSegment`. The real root cause was deeper: `mapEntry`
in `database.ts` hardcoded `complete: true` for every segment in `segments[]`,
which hid the open segment that `punchIn` writes. This made the new ClockPunch
UI see "no open shift" right after a successful clock-in, despite the toast
saying "Clocked in — shift started".

Three fixes in this pass:
1. `mapEntry`: respect persisted `s.complete` instead of forcing `true`
2. `getActiveSegment` / `hasOpenSegmentLocal`: short-circuit on
   `status === 'voided' | 'archived'`
3. `clockService.punchIn`: include `status` in the minimal `existing` shape
   so the validator can see the voided state

Plus infra: deploy script, cleanup script, admin test user, and preflight
voiding for the myshift e2e so the (B) classic flow can run after (A).

## Root cause analysis

### The original "UI flip" bug (pass 5)

The legacy `?classic=1` TodayEntry form's `setDoc` only wrote top-level fields
(`clockInManual`, `clockInSystemTime`, `currentStep`, `taskId`, `createdAt`,
`updatedAt`) — NEVER `segments[]` and NEVER `clockInSystem` (millis). The new
ClockPunch UI's `getActiveSegment` only inspected `entry.segments[]`, so it
returned `null` and the UI flipped to "CLOCKED OUT".

Pass 5 fix: a 3-tier fallback in `getActiveSegment`:
1. Canonical open segment in `entry.segments[]`
2. `entry.currentSegment` (synthesized view from `mapEntry`)
3. Synthesize from `clockInManual` if it's set and `clockOutManual` isn't

### Why pass 5's fix wasn't enough

The pass 5 tests passed, but the e2e (A) flow still showed "CLOCKED OUT" right
after a successful clock-in. Investigation showed:

1. `punchIn` dual-writes: it writes BOTH `segments: [openSeg]` AND the legacy
   top-level fields (`clockInManual`, `clockInSystem`, etc.)
2. `mapEntry` (in `database.ts:199`) hardcoded `complete: true` for every
   segment in `segments[]` because the comment said "Firestore stores
   *archived* segments in `segments[]`"
3. But `punchIn` writes a NON-archived (open) segment to `segments[]`
4. After `punchIn` finishes, the UI re-reads → `mapEntry` runs → forces
   `complete: true` on the just-written open segment → `getActiveSegment`
   sees no open segment in `segments[]` → falls through to legacy fallback
   → `clockInManual: 10:52 && !clockOutManual: 10:53` — but `clockOutManual`
   was a stale 10:53 from a previous test → fallback returns null → UI shows
   CLOCKED OUT

The 4-second "flip" was the round-trip of the post-write `load()` re-reading
the same half-baked doc.

### The voided-status bug (also found in this pass)

The `hasOpenSegmentLocal` function in `timeValidation.ts` (and its twin in
`segmentOps.ts`) checked `clockInManual && !clockOutManual && !complete` to
detect a legacy open shift. But it didn't check `status === 'voided'`, so a
soft-voided doc with an open segment in `segments[]` was still treated as
"open shift" — which made the `validateCanPunchIn` validator throw "You
already have an open shift today" even after the cleanup script voided the
doc. This is a real bug, not just a test issue: a manager who soft-voids an
employee's old half-baked doc would leave the next day's clock-in blocked
until the segments[] were manually rewritten.

Fix: short-circuit on `status === 'voided' || 'archived'` in both
`getActiveSegment` and `hasOpenSegmentLocal`.

### The clockService.punchIn status check (also found in this pass)

`clockService.punchIn` builds a minimal `existing` entry shape from
`snap.data()` to pass to `validateCanPunchIn`. The minimal shape included
`segments` but NOT `status`, so the voided short-circuit couldn't fire. Fix:
include `status: snap.data().status` in the minimal shape.
