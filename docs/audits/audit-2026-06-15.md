# TimeTrack — audit pass 5 (2026-06-15)

**Branch:** `main` (direct commit)
**Builds on:** `fix/clock-in+lunch+clock-out` (pass 4 + production bug fixes)

## Symptom reported by user

When an employee clicked **CLOCK IN** in the ClockPunch UI, the status flipped
to "CLOCKED IN" for ~4 seconds, then silently flipped back to "CLOCKED OUT"
while the Firestore data was still correct. Same for lunch and clock-out.

## Root cause (found via Firestore REST)

The user's prior Playwright test runs had used the legacy `?classic=1`
TodayEntry form to write a clock-in. That form's `setDoc` only wrote the
top-level legacy fields (`clockInManual`, `clockInSystemTime`, `currentStep`,
`taskId`, `createdAt`, `updatedAt`, etc.) — it never wrote `segments[]` and
never wrote `clockInSystem` (millis).

The new ClockPunch UI's `getActiveSegment` only inspected `entry.segments[]`.
With no segments, it returned `null`, so the UI showed "CLOCKED OUT" even
though the user was on the clock. A second load (triggered by the post-write
`load()` call inside `punchIn`) re-read the same half-baked doc and
re-rendered with `isClockedIn = false`.

The "4 seconds" was the Firestore SDK round-trip time of the second `getDoc`.

## Fix

`getActiveSegment` (and its private cousin in `timeValidation.ts`,
`hasOpenSegmentLocal`) now fall back through three levels before giving up:

1. **Canonical:** an open segment in `entry.segments[]`.
2. **Synthesized view:** `entry.currentSegment` (what `mapEntry` builds from
   the legacy top-level fields when `clockInManual` is set).
3. **Legacy half-baked:** if `clockInManual` is set, `clockOutManual` is not
   set, and `complete` is not true, synthesize a minimal open segment from
   the top-level fields.

This means: any doc that says "I have a clock-in time" is treated as an open
shift, regardless of which UI wrote it.

## Remaining risk surface

- **Pre-existing `punchIn` write conflict:** `punchIn` writes BOTH
  `segments: [openSeg]` AND the legacy top-level fields. `mapEntry` then
  assumes `segments[]` are all archived (forced `complete: true` on read)
  and synthesizes the current from the legacy fields. This works, but the
  `segments[]` is now treated as archived and the synthesized current
  takes precedence. Future `punchOut` reads `pre.segments` (which has the
  new open segment) and uses it as the basis for the next write. This is
  a known design quirk — not a regression from this audit pass.
- **No backfill on read:** if a user has a half-baked doc in the wild,
  their next `punchIn` or `punchOut` via ClockPunch will write the proper
  shape and self-heal. A backfill on next read would be nice-to-have but
  was deferred (low value, the fallback handles it correctly).
